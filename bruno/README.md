# API review with Bruno

Open this `bruno/` folder as a collection in Bruno. The requests already include file attachments, assertions, and document-ID capture; you do not need to import OpenAPI or assemble the requests yourself.

## Start the application

Use the existing untracked `.env` with `GEMINI_API_KEY`. Keep that key on the server: this API has no client authentication, and the collection contains no credentials.

For a separate manual stack, run from the repository root in a dedicated terminal:

```bash
export COMPOSE_PROJECT_NAME="bwai2-manual-$(date +%s)"
export APP_PORT=18080
export TEST_SUMMARIZER_ENABLED=false
make up
```

Both extraction modes normally call Gemini for the summary. The Gemini folder also sends the PDF to Gemini. The supplied fixtures are synthetic; use non-sensitive files if you replace them.

## Select an environment

1. Open the environment dropdown at the **top right** of Bruno. It may say **No environment**.
2. Select **Manual** for `http://127.0.0.1:18080`, or **Local** for the README's default stack at `http://127.0.0.1:8080`.
3. Leave `{{baseUrl}}` in the request URLs. The selected environment supplies its value. If your stack uses another port, edit `baseUrl` in that environment.

### If `{{baseUrl}}` appears red

Check that you have selected **Manual** or **Local**. This collection defines `baseUrl` in its environment files, not in each request.

If those environments are missing, open the repository's `bruno/` folder as a collection rather than using the earlier OpenAPI import. The folder includes `environments/Manual.bru` and `environments/Local.bru` with `baseUrl` already set. You do not need to replace the placeholder in every request.

See [Bruno's environment setup instructions](https://github.com/usebruno/bruno-docs/blob/main/introduction/quick-start.mdx#4-create-an-environment) for the dropdown location.

## Review the requests

| Folder | Requests | What to check |
| --- | --- | --- |
| Core | Health, PyPDF submission/result, two-file batch/results, corrupt PDF submission/result | Accepted jobs progress independently; good PDFs complete; corrupt PDF parsing fails in the worker |
| Validation | Retired parser, missing fields, wrong media type, bad signature, mixed batch, unknown/invalid IDs | Invalid submissions are rejected; a bad file rejects the entire batch |
| Gemini | Gemini submission/result | Native PDF extraction and a non-empty summary with a real configured provider |

Run each folder's requests in order. POST requests capture IDs as **runtime variables**, so sending requests does not rewrite the environment files. Those IDs disappear when Bruno closes; submit again after reopening it.

For each POST/GET pair:

1. Send the POST and expect `202` with queued document IDs.
2. Send the corresponding GET. Repeat it until `status` is `completed` or `failed`.
3. For good PDFs, expect a non-empty summary and ordered, zero-based pages. For `corrupt.pdf`, expect `failed` with `error.code: "invalid_pdf"`.

The GET assertions allow `queued` and `processing` while work is in flight. **A green GET test does not prove processing has finished.** Once terminal, the assertions require the expected outcome and validate the result or error payload. A failed document is still retrieved with HTTP `200`.

Readiness only checks Redis and summary configuration. `gemini: "configured"` does not validate the key against Google. `gemini: "test-only"` means the explicit fake summarizer is enabled, not that Gemini works.

## Fixtures

All attachment paths are relative to the collection folder.

- `sample.pdf` and `second.pdf`: identical, valid one-page PDFs with different filenames, generated by `scripts/generate_sample_pdf.py`. Their text is `Async document processor smoke test`.
- `notes.txt`: non-PDF media type, rejected during submission.
- `not-pdf.pdf`: a PDF filename without a PDF signature, rejected during submission.
- `corrupt.pdf`: starts with `%PDF-` but is not parseable. Submission accepts it; the PyPDF worker rejects it.

File-count and size limits are covered by the backend test suite. To review them manually in Bruno, attach 11 distinct PDFs or a PDF larger than 20 MiB and expect HTTP `413` with the default server settings. Large fixtures are not bundled.

## Optional CLI check

The collection was checked with Bruno CLI `4.3.0`. With Node/npm installed and the stack running:

```bash
cd bruno
npx --yes @usebruno/cli@4.3.0 run Core Validation --env Manual
```

This runs the HTTP assertions once. It does not wait for every job to become terminal; repeat the result requests in the app to finish the review.

Run the Gemini folder only when you intend to make live provider calls:

```bash
npx --yes @usebruno/cli@4.3.0 run Gemini --env Manual
```

The Core requests still use real Gemini summaries on a normally configured server. For a credential-free orchestration check, start a separate disposable stack with `GEMINI_API_KEY` empty and `TEST_SUMMARIZER_ENABLED=true`, then run only Core and Validation. That does not test Gemini extraction or summarization.

If you generate reports, keep them under the repository's ignored `.tmp/` directory. Reports can contain document data; use `--reporter-skip-body --reporter-skip-all-headers` when you do not need those payloads.

## Logs and shutdown

From the same terminal used to start the manual stack, at the repository root:

```bash
make logs
make down
```

`make down` keeps the Redis volume. Do not run the smoke, browser, or live-provider Make targets against a stack whose records you need: those targets delete the selected stack's volume.
